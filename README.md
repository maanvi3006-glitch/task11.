# Task 11 — Correlation & Heatmaps
**Data Analyst · Altrodav Technologies · PlaceMux Phase 1 Industry Immersion**

Quantifies and visualises relationships between Altrodav's daily business
metrics using correlation analysis and heatmaps, so the team can see what
moves together, what doesn't, and what's safe to act on.

## Quick start

```bash
pip install -r requirements.txt

# Interactive dashboard (recommended for live demo/marking)
streamlit run app.py

# OR: non-interactive run that writes evidence files to outputs/
python run_analysis.py

# Automated edge-case tests
python -m pytest tests/ -v
```

No external download is required — the dataset ships in `data/`. To verify
live behaviour with different data, use the file-uploader in the dashboard
sidebar, or pass any CSV path to `run_analysis.py`.

## How this maps to the Task 11 brief

### 1. What this task is / why it matters
Correlation quantifies *how strongly* and *in which direction* variables
move together; heatmaps make that instantly scannable across many
variables at once. Both are delivered here: numeric matrices
(`outputs/pearson_matrix.csv`, `spearman_matrix.csv`) and a rendered
heatmap, in both an interactive (Streamlit) and static (PNG) form.

### 2. Build pipeline — implemented step-by-step
| Step | Where |
|---|---|
| 1. Compute correlation matrix | `correlation_analysis.compute_matrices()` |
| 2. Render as heatmap, clustered | `correlation_analysis.cluster_order()` + `app.py` Heatmap tab |
| 3. Flag strongest relationships | `correlation_analysis.strongest_pairs()` |
| 4. Plausible driver vs coincidence | `correlation_analysis.classify_pair()` / `explain_pair()` |
| 5. Multicollinearity | `correlation_analysis.compute_vif()` (proper VIF, not just eyeballing) |
| 6. Summarise what's actionable | `correlation_analysis.build_summary()` / Dashboard "Written Interpretation" tab |

### 3. Alternative approaches — considered and implemented, not just discussed
- **Pearson vs Spearman**: both are computed for every pair. The dashboard
  lets you toggle which drives the heatmap, and any pair where the two
  disagree by ≥0.15 is explicitly flagged as "possibly non-linear" —
  directly answering the brief's own pitfall ("Ignoring non-linear
  relationships Pearson misses").
- **Full matrix vs targeted pairwise deep-dive**: the heatmap gives the
  full-matrix view; the "Strongest Relationships" tab gives the targeted,
  interrogated deep-dive on each strong pair. Both are in the deliverable,
  not a forced choice between them.

### 4. Core deliverable (50 marks) — a heatmap **with written interpretation**
- Heatmap: `app.py` "Heatmap" tab (interactive) and `outputs/correlation_heatmap.png` (static).
- Written interpretation: `app.py` "Written Interpretation" tab and
  `outputs/interpretation_report.md`. This is generated **from the live
  data**, not hard-coded prose — every r-value in the text comes straight
  out of the currently loaded matrix.

### 5. Real-data quality & correctness (20 marks)
- 736 rows / 2 years of daily data — a realistic operating scale, not a
  10-row toy.
- The dataset is **simulated, not hand-typed**, with genuine mechanistic
  relationships built in (`src/generate_data.py` documents exactly why
  each variable correlates the way it does), so the "right answers" the
  analysis should find are known and checkable — while still requiring
  real statistical work to uncover.
- Deliberately includes realistic messiness: missing values, duplicate
  rows, a units-error outlier batch, and wrong-dtype string artifacts —
  so "real inputs" also means "inputs that need cleaning," not a
  happy-path CSV.

### 6. Live verification & evidence (15 marks)
- `streamlit run app.py` is a genuinely interactive, live-recomputing
  dashboard: change the correlation method, change the strength threshold,
  or upload a different CSV in the sidebar, and every number and chart
  recomputes — nothing on screen is a static screenshot or hard-coded
  string.
- `run_analysis.py` is a second, independent way to produce the same
  evidence non-interactively (useful for a marker who wants file outputs
  rather than a running server).
- `tests/test_data_loader.py` (9 tests, all passing) is executable proof
  the failure-handling claims in this README are true, not just asserted.

### 7. Dependency, failure & edge-case handling (15 marks)
`src/data_loader.py` explicitly defends against and reports on:
missing/unreadable file, empty file, unparseable file, missing expected
columns, wrong dtypes / stray text in numeric columns, missing values
(median-imputed, not silently dropped), duplicate rows, and implausible
outliers (winsorised, not deleted, so nothing is quietly thrown away).
Every one of these is exercised by an automated test and surfaced to the
user with a friendly message instead of a raw traceback — try it live by
uploading a broken CSV in the dashboard sidebar.

### 8. Pitfalls avoided (from the brief)
- **"Reading causation into correlation"** — every strong pair in the
  interpretation is explicitly labelled *plausible driver*, *likely
  spurious*, or *needs domain review*; none are asserted as proven causal.
- **"Ignoring non-linear relationships Pearson misses"** — Spearman is
  always computed alongside Pearson, and divergent pairs are flagged.
- **"A rainbow heatmap with no takeaway"** — every strong cell is
  explained in plain language with an explicit action or non-action in
  the Written Interpretation tab; the heatmap never stands alone.

### 9. Brainstorming questions from the brief — answered in the deliverable
- *Believable causal story or spurious?* → `classify_pair()` /
  `explain_pair()`, surfaced per-pair in the dashboard.
- *Which correlated pair would distort a model and should be pruned?*
  → the VIF table (`compute_vif()`), which flags `website_traffic`,
  `ad_clicks`, `conversion_rate`, and `revenue` as candidates to prune
  before any downstream modelling.
- *What relationship did you expect but didn't see?* → covered explicitly
  in the "What we expected but didn't see" section of the Written
  Interpretation tab (`employee_count` vs `revenue`).

## Design notes / choices worth knowing about
- **Why simulated data instead of a public dataset?** It lets the
  submission guarantee the presence of a genuine driver chain, a
  deliberate multicollinearity pair, and a deliberate spurious/seasonal
  correlation — the exact phenomena Task 11 asks you to distinguish —
  while staying fully offline-reproducible and free of any third-party
  data-licensing question. `src/generate_data.py` is fully commented so
  every relationship's origin is auditable.
- **Why VIF instead of just "|r| > 0.8"?** Pairwise correlation can miss
  multicollinearity that only shows up across three or more variables
  jointly; VIF (Variance Inflation Factor) catches that properly and is
  the standard tool analysts reach for before feeding features into a
  regression/ML model.
- **Why hierarchical clustering for heatmap order?** An alphabetical or
  input-order heatmap scatters related variables across the grid; a
  clustered order groups them into visible blocks, which is what "ordered
  to reveal clusters" in the brief is asking for.
